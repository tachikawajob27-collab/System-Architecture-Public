# 定期通販の新基盤

購入、定期契約、決済、出荷、顧客対応を一つの管理基盤にまとめ、旧通販から新しい土台へ移行した仕組み。

## 利用者と課題

購入者、顧客対応担当、物流担当、広告・分析担当、管理者が利用する仕組み。

長く運用した通販では、購入画面だけでなく、定期契約・出荷・決済・通知に独自の業務ルールが蓄積する。土台を新しくしても、利用者や日々の業務が困らないようにする必要があった。

## 主な機能

| 機能 | 内容 |
|---|---|
| 購入と契約 | 広告の申込ページから購入し、契約内容や次回配送を確認・変更する。 |
| 管理業務 | 受注・定期契約・顧客対応・商品群ごとの管理を行う。 |
| 決済と物流 | 決済結果と受注状態を連携し、倉庫向けの出荷情報を作成・取り込む。 |
| 日次処理 | 定期受注の生成、決済後の処理、通知などを定期的に実行する。 |

## 処理の流れ

購入申込 → 入力確認 → 受注・契約登録 → 決済 → 出荷準備 → 出荷実績取込 → 通知

この流れは説明用の要約。実際の処理では入力確認、権限確認、例外時の対応などが加わる。

## 技術と役割

| 技術 | 役割 |
|---|---|
| PHP（ウェブ処理を書く言語） | 通販の処理本体 |
| EC-CUBE（通販サイトの土台となるソフト）の新しい世代 | 購入・商品・受注の基本機能 |
| Symfony（処理の組み立てを支える枠組み） | 画面の受付と業務処理の分担 |
| PostgreSQL（データを表の形で保存する仕組み） | 受注・契約・顧客関連の保存 |
| Twig（画面のひな形を作る仕組み） | 顧客画面と管理画面 |

## 設計上の見どころ

### 既存業務との一致を重視

画面だけでなく、金額計算、契約の扱い、通知、出荷の条件を照合する。

### 判断条件を分離

出荷対象の選び方などを、接続処理を持たない小さな処理に分けて確かめる。

### 移行と日常運用を分けて確認

移行用処理、日次処理、画面操作を別の観点で確認する。

## 刷新の進め方

旧世代（EC-CUBE 2系：PHP・Smarty）から新世代（EC-CUBE 4系：PHP 8.3・Symfony 7・Doctrine・Twig・PostgreSQL 14）へ、650件以上の独自改修を移した。2026年10月に本番を切り替え、現在は新基盤で運用している。

```mermaid
flowchart LR
  P1["旧機能の棚卸し"] --> P2["機能ごとに移植"]
  P2 --> P3["新旧の対比テスト・検証"]
  P3 --> P4["本番切替"]
  P4 --> P5["切替後の運用・修正"]
```

### 段階を分ける

移植、テスト・検証、本番切替を別の段階として進める。切替前に対応が必要なもの、技術的な負債、切替後に検証するものを、課題の種類として分けて管理する。

### 新旧の名前の違いを対応表にする

同じ役割の表でも、新旧で表名や項目名、状態の持ち方（削除の印、主キーの名前など）が変わっている。旧の問い合わせ文をそのまま使うとエラーになるため、対応表を作り、移植のたびに参照・追記する。

### 「同じ結果になるか」を記録する

機能ごとに、同じ入力（操作・データ）を新旧に与えたときの結果を並べた対比データを残す。動くことだけでなく、旧システムと同じ結果になることを確かめるため。

### 変更のたびに自動で確かめる

| 確認 | 内容 |
|---|---|
| 画面操作の自動テスト（Playwright） | 新しい画面や処理を加えるたびに1本追加する。注文を作るテストでは、画面の表示だけでなく、データベース上の注文状態まで確かめる。 |
| 生成AIによる新旧比較レビュー | 変更ごとに、旧コードと新コードを並べて、処理の流れが踏襲されているか、仮の値が残っていないか、対象外の範囲が明記されているかを確認させる。 |
| 自動の検査（CI） | 変更を取り込む前に、静的解析（実行せずにコードの誤りを探す検査）やテストを自動で実行する。 |
| 環境の一致確認 | 稼働中の環境と、記録しているソフトの版・構成が一致しているかを確かめる。 |

### 本番以外からの誤送信を防ぐ

決済や通知など外部へ送る処理は、本番以外の環境では送信を止める仕組みを通す。試験中の操作が、実際のお客様や取引先に届かないようにするため。

### 後回しを残さない

「次の変更で直す」とした事項は、その場で課題として登録し、切替前に必要かどうかを分けて管理する。
