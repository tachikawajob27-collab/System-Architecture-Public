# 旧通販の管理と自動処理

受注管理、定期受注、決済後の処理、出荷、集計を支える社内向けの仕組み。

## 利用者と課題

受注担当、顧客対応担当、物流担当、広告・分析担当が利用する仕組み。

定期通販では、注文を受け付けた後にも、継続受注、支払結果の反映、倉庫への依頼、出荷実績の取込が発生する。担当者の操作と自動処理が同じ受注状態を扱う必要があった。

## 主な機能

| 機能 | 内容 |
|---|---|
| 管理画面 | 受注、顧客、契約、広告に関する情報を確認・変更する。 |
| 定期処理 | 契約に基づく受注生成や決済後の処理を実行する。 |
| 出荷連携 | 倉庫向けの表形式データを出力し、出荷後の結果を取り込む。 |
| 集計と通知 | 業務結果を集計し、確認が必要な状態を担当者へ知らせる。 |

## 処理の流れ

契約・受注情報 → 定期実行 → 決済結果反映 → 出荷対象選択 → 倉庫連携 → 実績更新

この流れは説明用の要約。実際の処理では入力確認、権限確認、例外時の対応などが加わる。

## 技術と役割

| 技術 | 役割 |
|---|---|
| PHP（ウェブ処理を書く言語） | 管理画面と定期実行処理 |
| EC-CUBE（通販サイトの土台となるソフト）の旧世代 | 受注・顧客・商品管理 |
| SQL（保存されたデータを問い合わせる言語） | 検索と業務集計 |
| CSV（表形式の数値や文字を保存する形式） | 倉庫等との情報受け渡し |

## 設計上の見どころ

### 受注状態の連携

決済済み・出荷準備中・発送済みなどの状態で処理対象を区別する。

### 外部処理の結果を取り込む

決済や倉庫の処理は受付だけで終わらず、結果を受注へ反映する。

### 画面操作と自動処理の関係

担当者の修正や解除が次の自動処理にどう影響するかを整理する。

## 紹介する範囲

実際の顧客データ、倉庫の契約番号、決済設定、過去の出荷ファイルは収録していない。

個人ごとの設計・実装・運用の分担や成果の数値は、元資料だけでは確定できないため断定していない。
